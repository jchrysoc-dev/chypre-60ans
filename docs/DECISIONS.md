## M3: activity sign-ups and RSVP (decided 2026-10-23)

| Date | Question | Answer | Why |
|---|---|---|---|
| 2026-10-23 | Who is signed up | An adult **ticks which household members** go (e.g. 2 of 4). Every person, child or adult, takes one place. Children can't be ticked for activities with `kid_friendly: false`. Organisers can override. | Families often split up for activities. Children still take a seat on a boat. |
| 2026-10-23 | Waiting-list promotion | **Groups stay together.** People signed up in one go form a group, and a waiting group is promoted only when all of it fits. A smaller group further back may go first if it fits. Queue order is the sign-up's identity id (strictly increasing), not a timestamp. | Never splits a family. Timestamps tie within one transaction. |
| 2026-10-23 | Changing sign-ups | Guests can sign up and cancel **until the activity starts**. Organisers can change them at any time. Cancelling deletes the row (no history). | Simple, and keeps the least personal data. |
| 2026-10-23 | RSVP first | Only people whose RSVP is **yes or maybe** can be signed up. Changing an RSVP to **no** removes the person from activities that haven't started (a database trigger), and the RSVP page says so. Organisers can sign up anyone. | Mum's headcounts only include people who are coming. |
| 2026-10-23 | RSVP form | **Part of M3.** One form per household with attending, arrival/departure dates, flights, and dietary needs (saved only with the consent box ticked; the consent time is kept). | The `rsvps` table already existed, and activities depend on it. |
| 2026-10-23 | Capacity in the database | `public.activities` is a trusted copy of `content/activities/*.md`, **written only by the server** with the secret key (`public.sync_activities`). It is synced once per server instance and again whenever the bundled content differs, before the Activities pages load and before any sign-up. Each row carries the build time (`__BUILT_AT__`), so an older server can't overwrite newer content. An empty list is ignored. **Vercel preview deploys don't sync.** | A guest can call Supabase directly with their login, so the limit must be enforced in Postgres. No build-time database writes, and `npm run check` still needs no secrets. |
| 2026-10-23 | How sign-ups are written | Guests have **no insert or update privilege** on `activity_signups`. Sign-ups go through `public.sign_up()` (security definer), which locks the activity row, checks the rules, and decides confirmed vs waitlisted. Cancelling is a plain `delete` under RLS, and a statement trigger promotes the waiting list after any delete, including cascades when a person or household is removed. | Guests can never choose their own status. Promotion happens in one place. |
| 2026-10-23 | What guests see | Every activity, their own household's sign-ups, counts per activity (`activity_overview`), and how many people are ahead of their waiting group (`my_waitlist_positions`). **No names from other households** (the participants directory is M4). | Privacy first. |
| 2026-10-23 | Capacity changes | Raising `capacity` promotes waiting groups on the next sync. Lowering it **never removes anyone already confirmed**. | Nobody loses a place they were given. |
| 2026-10-23 | Stopping an activity | `status: cancelled` in the content file. The page shows it as cancelled, sign-ups freeze, and admin still lists who had signed up. **Don't delete activity files.** If one is deleted anyway, its row is marked `in_content = false` and its sign-ups are kept and listed in admin under the activity, marked "No longer on the website". | Mum's agent can't see the database, so deleting would silently lose sign-ups. |
| 2026-10-23 | Admin pages | `/admin` (Guest list), `/admin/rsvps` (Replies: counts, not replied, arrivals/departures, flights, dietary), and `/admin/activities` (headcount with adults and children, who is going, waiting list in order with groups). On the Activities page, Mum can sign anyone up, give a place over capacity (also to someone already waiting) and remove anyone. Two CSVs: `/admin/activities.csv` and `/admin/rsvps.csv`. The footer link is now "Organisers". No money summary. | What Mum asked for. |
| 2026-10-23 | CSV format | UTF-8 with a byte-order mark and CRLF line endings. Values starting with `= + - @` get a leading `'`. Times are written in **Cyprus time** as `2027-05-27 10:00` (columns end in `_cyprus_time`). File name is `<name>-YYYY-MM-DD.csv`, dated in Cyprus. | Opens correctly in Excel and Google Sheets, a guest's name can't become a formula, and Mum reads the times as she knows them. |
| 2026-10-24 | Blocked tick boxes | A person who replied "no" shows "Not coming to the party (change the reply)", which is different from "Reply to the invitation first" for people who haven't replied. | Found in browser testing: the old label was wrong for people who had replied. |
| 2026-10-24 | Sync robustness | If the build time is missing (a dev server started before `astro.config.mjs` defined it), the server's start time is used instead. Any sync failure is logged and never breaks a page. | Found in browser testing: a long-running dev server crashed /activities. |
| 2026-10-23 | Notifications | None. A promoted guest sees "Going" on the Activities page. Mum sees "From the waiting list" with the time in admin and in the CSV. | Already settled: no emails from the site. |
